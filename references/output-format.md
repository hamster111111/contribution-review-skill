# 可读的贡献评语

完整评审默认用Markdown：**简短总览 → 逐项原稿／问题／论文对照／改法 → 样本索引**。局部问题只保留有用部分。按用户指定输出格式交付；没有要求保存文件时直接在对话呈现，需文件时以.md为主，JSON仅按需另存。

## 开头：让读者先知道结论

用一个标题，随后简短交代待评版本／原稿入口、一句话idea、总体判断及最值得保留的具体优势。要求打分时列贡献部分ARR式分数及主要依据，相邻档理由一句即可。只列优先处理的1–2项；没有必改项就写“无必改项”，不要造出问题填模板。稿件占位、计划或缺必要上下文的状态在相关处说明一次，避免反复免责声明。

## 正文：每项就地放齐信息

一项一个二级标题，直接说具体内容，例如“可选优化1：在贡献汇总中突出新增评价对象”，避免只写“逻辑问题”“创新性不足”。按实际判断使用“必须修改”“可选优化”或“值得保留”，不将可选润色叫作核心缺陷。通常重点展开1–2项，实际需要更多时不遗漏。

每项用以下短标签展开，不写连续长论证或把几篇论文分别讲完后才给建议：

1. **原文位置**：C2等段落／句子定位，并附可用的原稿或快照链接；摘录足以识别问题的短原句。不要只有抽象编号、没有可找回的原文。
2. **问题与影响**（正面项用“优点与作用”）：说明哪两端未连接或已经连接、为何影响当前承诺。必要修改说明最小收窄会保留／失去什么；局部问题不升级为内容失效。
3. **别人怎么写｜S1**：简写论文、会议年份、已核验团队背景，指出具体章节／页码并链接原文。用一两句话说明写作动作，再说明与本稿的对应或差别。概括标明“原文概括”，逐字引文另用引用块且保持短小；不得把概括伪装成原句。范例原文必须在这条意见旁可点击，不只留到末尾。
4. **建议怎么改**：给出能执行的最小动作，区分必改与可选；正面项可以说明保留什么。以用户已有内容为限，不补造机制／结果；只有用户要求改写时才附完整替换段落。

这四部分可以短写，事实足够清楚时不用机械重复。找不到足够可比样本时如实说明，保留基于本稿成立的判断，不编引文或把引用缺失当本稿缺陷。无问题也可用“值得保留”项解释已成立的写法，无需制造一个可选修改。

## 末尾：样本在哪里

给一个紧凑的样本索引，S1、S2等编号与正文一致。建议列“编号／论文与会议年份／用于哪项／原文位置与链接”，每格只放短信息，不塞长段落。团队只需一次简写和来源，详细作者单位映射、评分历史、缓存校验等放结构化记录或附件。

原文稿件与对照论文分别标明入口；给出真实页码、章节或行号，不编定位。若使用高分背景，在对应引用旁简短注明分数字段与记录日期／阶段，长核验过程不挤占正文。出处不可靠时明确已知与未知。

## 排版与对应

短段落优先；长原句用引用块，不把引文、背景或修改方案塞进宽表。只用必要的标题、加粗和列表，不用大量装饰。相同论文统一用一个样本编号，可服务多项意见；索引列实际用到的样本，不堆未解释的参考文献。

若另存JSON，可用review_items对应正文条目，并用sample_ids关联exemplars中的sample_id；必要问题仍进入top_issues，可选项不冒充必改。Markdown和JSON判断、分数及引用一致。完整评语读起来应能直接回答：问题是什么、在哪里、别人如何处理、建议怎么做、原文样本去哪里看。
