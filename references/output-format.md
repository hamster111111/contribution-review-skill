# ARR 式可读贡献评语

完整评审默认用Markdown：**Summary → Strengths → Weaknesses → Suggestions → ARR维度评价 → 样本索引**。先总结与分析，再给分项判断；局部问题只展开相关内容，不强填整套报告。需文件时以.md为主，JSON仅按需另存；用户指定格式优先。

## Summary 让读者先理解内容

一个标题，简短交代待评版本／原稿入口、一句话idea及总体判断。说明一次“以下为贡献部分的ARR式适配”，不是全文科学可靠性或录用预测。计划、占位和缺必要上下文的状态在相关处说明，不反复加免责声明。

## Strengths 已成立的具体价值

通常写1–3项：具体新增什么、相对什么起点、对哪些判断或能力有价值。不要只写清晰、有趣、有创新性；也不把同一关系换几个名字当作多项独立贡献。可用“值得保留”项说明好在哪里，未必都需修改或引文。

## Weaknesses 必须处理的问题

只列实际影响当前承诺的必要修改，分清核心、有界实质与局部问题。无必改就写“无必改项”；Overall为3同样可以没有必改项。重要问题多于通常的1–2项时不遗漏，不能为了严格凑缺陷。

## Suggestions 可选改进

放确有用途的可选润色、组织优化或建议；必要修改动作已在Weaknesses对应项写清时，只简短引用其优先级，不重复一套论证。用户未要求时不附完整替换段落。

## 每项就地放齐信息

Weaknesses与展开的Suggestions一项一个具体标题，例如“可选优化：在贡献汇总中突出新增评价对象”。保留以下短标签，能短写时不机械重复：

1. **原文位置**：C2等段落／句子定位，加可用稿件链接及短摘录，不能只有抽象编号。
2. **问题与影响**（正面项用“优点与作用”）：说清已连起或未连起哪两端。必要修改说明最小收窄会保留／失去什么，局部阅读负担不升级为内容失效。
3. **别人怎么写｜S1**：简写论文、会议年份、核验团队，给具体章节／页码及一手原文链接；用一两句话说明写作动作与本稿的关系。概括标明“原文概括”，不能冒充原句；逐字引用保持短小。
4. **建议怎么改**：给最小可执行动作并标明必改或可选，以已有事实为限，不补造机制或结果。

对照论文就近可点击，不先把几篇论文各讲一大段再给建议。找不到足够可比范例时如实说明，保留基于本稿的判断，不编引用，也不把引用缺失当本稿缺陷。

## ARR维度评价 独立判断各项

按 [arr-dimensions.md](arr-dimensions.md) 给紧凑四行表：**维度／分数或文字判断／本稿依据**。对应Soundness贡献论证支持度、Excitement贡献兴趣与潜在价值、Overall贡献综合判断、Reviewer Confidence本次判断把握。

请求打分或ARR式评审时，三项质量分使用1–5半分，Confidence只用1–5整数；只要单一分数或明确不要数字时遵守。没有请求数字的普通完整评审使用文字判断，不填假分。质量分必要上下文不足时可为null，标明不能判断什么。

各行依据要回答不同问题。Soundness说明给定素材内的论证与范围，不冒充全文实验核验；未查的实证与复现就近记为未评。Excitement说明具体受益者与值得关心的认识／能力，不能照抄“清楚”。Confidence不是质量分。Overall按 [scoring.md](scoring.md) 单独判断，不取各项平均；高于3指明具体越档价值，相邻档理由简短说明即可。不要因Soundness为4就把Overall也填4。

## 样本索引 范例在哪里

给紧凑索引，S1、S2与正文一致。建议列“编号／论文与会议年份／用于哪项／原文位置与链接”，不塞长段落。团队一次简写附来源，作者单位映射、评分历史和缓存校验留结构化记录或附件。

待评稿和对照论文分清入口，不编页码或定位。若提高分背景，在相应引文旁注明字段、日期／阶段；未核验就说未核验，不以录用或奖项换成数字。

若另存JSON，review_items对应正文条目，sample_ids关联范例；必要问题仍进top_issues，可选项不冒充必改。arr_dimensions记录Soundness、Excitement和Confidence，Overall放overall_score／overall_rationale，避免复制出不一致的两个Overall。Markdown、JSON、判断和分数保持一致。
